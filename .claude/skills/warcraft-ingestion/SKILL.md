# warcraft-learner ingestion & content pipelines

The CLI scripts are TypeScript run via `tsx` (e.g. `tsx --tsconfig tsconfig.scripts.json scripts/ingest/orchestrator.ts`), not `.mjs`/`node`. `WCL_CLIENT_ID`/`WCL_CLIENT_SECRET` come from the [Warcraft Logs API clients](https://www.warcraftlogs.com/api/clients/) page and are only used server-side (GHA secrets), never in the browser. Rulebook generation is the **warcraft-rulebook** skill (Claude-driven, no external LLM key); this skill covers how ingestion consumes rulebooks. The `npm run ingest` / `npm run rulebook:publish` invocations are listed in CLAUDE.md.

## Ingestion (`npm run ingest`)
Runs `frontend/scripts/ingest/orchestrator.ts`, which boots a headless Angular runtime (`scripts/ingest/angular-runtime.ts`: jsdom + Angular TestBed injector wired to the Node WCL + data-file transports) and drives the SAME five `*TransformService`s the browser uses, persisting through the SAME `DataFileApiService` (Node filesystem transport). There is no separate Node analysis pipeline. Also runs as the `ingest-parses.yml` GHA hourly and on manual `workflow_dispatch`. Before discovery it resolves the full spec universe (class/spec names + slugs, icons) from WCL `gameData.classes` (`mapClassesToSpecMeta`), hydrates the runtime's spec-meta cache so `getRankings` resolves, and bakes `spec-meta.json` for the browser - no hardcoded spec table.

1. Boots the Angular runtime and authenticates to WCL with client credentials (from `WCL_CLIENT_ID`/`WCL_CLIENT_SECRET` environment variables - server-side secret, only used in GHA, never in the browser). Per spec it runs a two-part **pre-flight** before any transform: (a) schema-validates `rulebook.json` (`validateRulebook`), and (b) an **integrity gate** (`rulebook-spell-ids.ts`) that resolves every rulebook spell id (cooldowns, defensives, both rule-condition kinds) against WCL in one batched `getAbilities` query and **skips the spec** if any id is unresolvable. Rulebook ids are LLM-guessed; a nonexistent id resolves to `null`, `abilityIcons` skips nulls, and a card's `ability_icons[id].icon` lookup would then throw - so a bad id is caught here (loud, no data written) rather than blanking a card at runtime (the "complete ingested data, no fallbacks" principle).
2. Discovers the specs that have a `rulebook.json` and the current live encounters (`getEncounters`: `worldData` discovery + a cheap rankings liveness probe). **Spec work-order** (`ordering.ts`, all cheap disk + git reads, zero WCL budget): empty specs first, then **old-version** specs (any on-disk file below the current `INGEST_VERSION`), then **current-version** specs, and within each group **oldest git-commit time first** (`git-mtime.ts` reads the last commit touching the spec's data dir - the workflow checks out with `fetch-depth: 0` so this is meaningful). So a budget-bounded run fixes the most out-of-date data first instead of starving the alphabetically-late specs.
3. Per encounter: asserts remaining WCL budget, fetches rankings (cheap), computes a version+ranking `source_signature` (`sha256(INGEST_VERSION + parse-set fingerprint)`), and **skips** the encounter when the signature matches the stored stamp. `INGEST_VERSION` (`ingest-version.ts`) is a **manual integer** that replaced the old transform-source code-hash: bumping it invalidates every cached file. Because transform-file edits no longer auto-invalidate, **Claude bumps `INGEST_VERSION` (or suggests bumping it) as part of any change that should produce different tailored data** (transform math, rulebook semantics, a deliberate refresh). The live value is the integer exported from `ingest-version.ts`.
4. Otherwise runs the five transform services (`burst`/`rotation`/`defensive`/`gear`/`map`) under bounded concurrency. Each fetches the parses it needs (`Casts`/`Buffs`/`DamageDone`/`DamageTaken`, plus `includeResources`/`hostilityType` events for positions) via the shared cached `WclApiService` and computes its slice.
5. Writes the stamped per-slice tailored files (`{spec}/{burst,rotation,defensive,gear}/{enc_id}.json`) and per-parse position timelines (`positions/{enc_id}.json`); every file carries both `source_signature` and the bare `ingest_version` integer.
6. Rebuilds the `{spec}/encounters.json` and top-level `index.json` indexes, then prunes stale encounters.

The data files are written **minified** (no pretty-print): machine-read only and thousands of them, so dropping indentation cuts the footprint ~70% while staying valid JSON. `node-data-file-transport.ts` (slice/index/positions/spec-meta writer) emits compact JSON; `rulebook.json` stays pretty (hand-authored).

`frontend/public/data/specs/**` is **not tracked on `main`** (it is gitignored there). It lives once on the **`gh-pages` branch at the site root under `data/specs/`** - the single shared copy the deployed site serves, and `ingest-parses.yml` is its only writer. Each run overlays the current `origin/gh-pages` `data/specs/` copy into the working tree before ingest (so signature-skip has the latest data on disk to compare against - `git archive origin/gh-pages data/specs | tar -x`), then publishes the resulting `frontend/public/data/specs` back to `data/specs/` on `gh-pages` via a single-commit, target-folder-scoped deploy (`clean:true` replaces `data/specs/` only, never `main/` or the `pr-*` previews). The action commits nothing when the tree is byte-identical, so quiet hours produce no push. The site reads this copy directly (absolute `dataBaseHref`), so publishing the data **is** the deploy - no code rebuild needed, and code deploys (`deploy-pages.yml`, which builds only the `main/` shell) never re-push the dataset. All three `gh-pages` writers (`ingest-parses`, `deploy-pages`, `pr-preview`) share **one `gh-pages` concurrency group** so their single-commit force-pushes serialize instead of reverting each other. For local dev, run `npm run data:pull` (from `frontend/`) to fetch and extract the data into your ignored working tree.

> **Keep data shapes in sync.** Because ingestion runs the very same `*TransformService`s the browser uses, the tailored slice shapes are defined in exactly one place - each slice's `*Bench` interface (its `*-data-source.ts`) plus the relevant `core/models/*` - and ingestion writes precisely those, so the slice shapes stay in sync automatically. Changing a slice's `*Bench`/model therefore updates runtime and ingest at once (one implementation). You still keep the rulebook schema (`rulebook.schema.json` in this skill's directory) in sync with the transforms (they consume the rulebook's `duration`/`spell_id`s) and with the **warcraft-rulebook** skill that generates rulebooks. The data-file shapes are defined in code - see "Data file shapes" below. Already-committed JSON under `data/specs/**` keeps stale fields until the next re-ingest - harmless, since consumers ignore unknown fields.

## Rulebooks
Rulebook generation is the **warcraft-rulebook** skill (Claude-driven: SimC + Wowhead + WCL grounding, one subagent per spec). This skill covers only how ingestion consumes them:

1. **Pre-flight** (per spec, before any transform): schema-validate `rulebook.json` (`validateRulebook`, `frontend/scripts/lib.ts`), then the **integrity gate** (`rulebook-spell-ids.ts`) resolves every rulebook spell id (cooldowns, defensives, both rule-condition kinds) against WCL in one batched query and **skips the spec** if any is unresolvable. A nonexistent id resolves to `null`, `abilityIcons` skips nulls, and a card's `ability_icons[id].icon` lookup would then throw - so a bad id is caught here (loud, no data written) rather than blanking a card at runtime. The schema requires at least one `major_cooldowns` and one `defensives` entry (`minItems: 1`). Ingestion is the single validation authority; the generation skill does not re-run it.
2. **Publish** (gh-pages only): rulebooks are gitignored on main and live on gh-pages. `npm run rulebook:publish` copies the local `rulebook.json` files into the gh-pages `data/specs/` tree; re-benching a changed rulebook needs an `INGEST_VERSION` bump or an ingest dispatch (the signature does not hash rulebook content).

## Data file shapes

The data files ingestion writes are deliberately **not** schema-documented here - read each shape from its source of truth so the docs cannot drift:

- **Rulebook** (`rulebook.json`) - `rulebook.schema.json` in this skill's directory: the authoritative contract (validated by `frontend/scripts/lib.ts`); generation is the **warcraft-rulebook** skill. All spell IDs come from the rulebook, never hardcode spec-specific IDs. The rule-engine condition kinds (`cast_without_prior`, `hold_cooldown_for_anchor`) are defined in the schema and the rotation rule-engine code.
- **Slice benches** (`{burst,rotation,defensive,gear}/{enc}.json`) - each slice's `*Bench` interface in its `*-data-source.ts`, plus `core/models/*`.
- **Indexes** (`index.json`, `spec-meta.json`, `{spec}/encounters.json`) - `core/models/*` (incl. `spec-meta.models.ts`) and the orchestrator's `rebuildSpecIndex` + spec-meta bake.
- **Signature stamps** (`source_signature`, `ingest_version`, on every slice + positions file) - `scripts/ingest/ingest-version.ts` + `signature.ts`.
- **Positions** (`positions/{enc}.json`) - `core/models/positioning.models.ts`; see the **warcraft-wcl-data** skill for the WCL position/facing-unit quirks behind it.
